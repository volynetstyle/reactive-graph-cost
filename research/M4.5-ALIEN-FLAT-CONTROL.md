# M4.5 control: Alien with its relational state in flat client lists

Question, from [M4B-SALSA-SYNTHESIS.md](M4B-SALSA-SYNTHESIS.md): does a client that reads
both axes need more than the flat per-node lists that sufficed for WPF and Salsa?

"Outside the store" alone is not a test for Alien. The frozen `alien-signals@8734d38` has no
store, and its own `Link` objects already pass its corpus. So the control asks something
narrower: `adapters/alien/control/backend-flat.ts` replaces the port's store with two ordered
arrays per node and a plain record per relation. Run with
`node adapters/alien/control/run.mjs`. `CONTRACT.md` is unchanged.

| Check | Result |
| --- | --- |
| corpus | 198 of 198 |
| public-API search against frozen | 0 of 4,000 differ |
| public-API search against `wide-fix` | 0 of 4,000 differ |

## What the client had to keep

| Kept | L0 capability it replaces |
| --- | --- |
| a record per relation, with both endpoints | identity, endpoint access |
| an array of relations per node, on each side | dual incidence, order on both axes |
| insertion at a position in the left array | positioned insert |
| a version word on the record | payload |
| `prevDep`, `prevSub` | predecessor state |
| `frozenNextDep`, `frozenNextSub`, a removed flag | post-removal state |

## Reading

- Flat lists are behaviourally sufficient. Alien does not need linked structure for its
  semantics in the tested domain.
- It still needs **both** ordered lists: its validation walks dependencies and its
  propagation walks subscribers. WPF and Salsa read one list. That is the difference between
  them and this client, and it does not depend on where the lists live.
- The cost moved out of sight. `next` and removal here use `indexOf`, so they are linear in
  degree, where clause 15 asks for constant time on a known handle. Keeping that bound is
  what brings a client back to linked records. This was not measured.
- Removal needs the record to stay readable and its successors to be saved. As in R5, the
  client holds that itself.

## What this does and does not settle

| Claim | Status |
| --- | --- |
| Alien's relational state can live wholly in the client | yes; true of the frozen source too |
| flat ordered lists suffice for its behaviour | supported |
| clients divide into one-directional and bidirectional | supported for WPF and Salsa against Alien. Quant, by its M1 inventory, reads both, but was not run this way |
| a bidirectional shape has to be a VM primitive | **not shown**: every client above runs without one |
| a store is cheaper or simpler for it | not measured: no bytes, no time, and bounds only by reading |

So behaviour no longer distinguishes any store design from a client one, across five clients.
What could still justify a primitive is physical: bounds, layout, GC integration with weak
endpoints, or real collectors, none of which a reference model in JavaScript can show.
